## 中文

当你已经把**普通、低敏感**附件发出，后来发现漏附、选错文件或用了旧版时，加载这份 Skill。目标是让原本该收到文件的人明确知道**哪一份才有效、要做什么**。若文件含个人隐私、财务/医疗/组织机密，或误发给无权收件者，先停止扩大传播并按相关平台/组织流程求助；本篇不评估泄露后果。

### 准备与输入

打开“已发送”里的原消息，核对实际收件人、发送时间、主题和附件名或分享链接。确认正确文件的内容、版本标识、页数/大小等你能现场核实的特征；不要只信文件名。先判断原件是已发出的**实体附件**还是受权限控制的**链接**，两者的撤回能力不同。不要把已编辑但未保存的文件重新误发一次。

### 执行

1. **先看有没有真正可用的取消。** 如果刚发送且界面仍显示“撤销发送”，可点它并核对消息是否回到草稿，再改附件。这个窗口依应用而异，过了就承认已发出。某些组织邮件的“召回”只在严格条件下有效；只有看到实际成功报告，才可说旧消息被召回，不用它代替更正通知。
2. **锁定有效版本。** 在本机打开正确文件，核对关键内容和可读性；写一个对收件人有用的标识，如“会议要点 9 月 28 日修订版”。若正确版本还没准备好，先发简短说明“前件请暂勿据此行动，正确附件将在确认后补发”，不要为了抢时间发第三个猜测版。
3. **给原目标收件人一条明确更正。** 核对 To/Cc 与原本有权接收的人；不要机械“回复所有人”。同一话题回覆通常方便对照，但先确认收件对象。简短写：“上一封的附件/链接是旧版（或漏附）；请以本封的《名称/版本》为准。请勿按前件继续处理。已开始处理的请告诉我当前进度。” 不说“更新了”却不说明哪份有效。
4. **附上并再次检查。** 用邮件或平台允许的附件/链接方式加入正确文件，发送前看附件已完成上传、打开预览可读、收件人与权限正确。若是链接，只在你有权更改其访问范围时按当前平台界面核权限；收紧链接权限不保证别人没有下载旧副本。
5. **核对发出和需要的回应。** 看“已发送”中更正消息确已出现；若对方需要据此执行有时间要求的动作，通过允许渠道请求其确认使用了正确版本。没有答复就标“未确认”，不能把自己发出当成对方已替换或已删除旧版。

### 完成、常见问题与补救

你已向正确对象发出一条可读的正确文件和无歧义版本说明，并如实标记对方是否确认。成功不要求旧附件被神奇地从所有邮箱消失。

- **还没拿到正确文件：** 先发“前件暂停使用”的事实通知，待核好再补，勿把猜测版标“最终”。
- **第二封仍没有附件：** 在已发送中核对；若确实漏了，再发一条简短且准确的补件说明，不悄悄改原说法。
- **收件人已按旧版行动：** 请其说明目前做到哪一步，再按普通协作流程协调修正；不要假定一句“忽略前件”会撤销已发生的工作。
- **召回按钮显示“已请求”或失败：** 仍把旧件视为可能可见，发送明确更正；不要宣称撤回成功。
- **无法确认内容或收件人：** 暂停再发文件，先核文件和授权对象；涉及敏感/受管信息时转适当支持。

### 假设、替代与现实副作用

邮件、聊天与云盘的撤销、权限和附件上传行为各异；按当前应用实际状态和组织要求核查，不把一个产品的按钮当普遍能力。读屏或移动端可用附件名称、大小、预览和收件列表核对。你需要多发一条消息，但清楚的版本标记减少继续使用旧件的机会；不能保证别人已经删除旧副本。

## English

Load this Skill after you have sent an **ordinary, low-sensitivity** attachment and discover it was missing, the wrong file, or an old version. The goal is for the people who should receive it to know **which copy is valid and what to do**. If the file contains personal, financial, medical, or organisation-confidential material, or reached someone without access rights, stop further distribution and use the relevant platform or organisation support route. This Skill does not assess disclosure impact.

### Preparation and inputs

Open the original item in Sent and check actual recipients, time, subject, and attachment name or share link. Open the correct file and check its content, version marker, page count, or size rather than trusting the filename alone. Decide whether the old item was a sent **file attachment** or a **permission-controlled link**; their recall options differ. Do not resend an edited but unsaved copy.

### Execution

1. **Check for a real cancellation option.** If the interface still shows Undo Send, use it and confirm the message returned to a draft before replacing the attachment. That window varies by app; after it closes, treat the message as sent. Some organisation mail can recall under narrow conditions. Claim recall only after an actual success report, and do not use a recall request in place of a correction.
2. **Lock the valid version.** Open the right local file, confirm key content and readability, and note an identifier useful to readers, such as “meeting notes, revised 28 September.” If it is not ready, send a short factual notice: “Please pause action on the previous attachment; I'll send the correct one after checking.” Do not rush out a third guessed version.
3. **Send a clear correction to the intended recipients.** Check To/Cc against people entitled to receive it; do not blindly Reply all. Replying in the thread can help comparison when the audience is right. Say, “The previous attachment/link was outdated (or missing). Please use ‘name/version’ in this message. Please do not continue from the earlier copy. If you have started, tell me where you are.” “Updated” alone does not identify the valid file.
4. **Attach and check again.** Add the correct file or link by a method the platform allows. Before sending, confirm upload completion, readable preview, recipients, and access scope. For a link, change access only when you are entitled to do so in the current platform. Restricting a link does not guarantee no one downloaded the old copy.
5. **Check sending and any needed reply.** Confirm the correction appears in Sent. If time-sensitive work depends on the file, ask for confirmation through an allowed channel that the right version is in use. Without a reply, mark “not confirmed”; sending does not prove that readers replaced or deleted the old copy.

### Success, common problems, and recovery

You sent a readable correct file to the intended recipients with an unambiguous version notice, and honestly marked whether they confirmed receipt. Success does not require the old attachment to vanish from every inbox.

- **The correct file is not ready:** Send a factual “pause using the previous copy” notice, then attach only after checking; do not label a guess final.
- **The second message also lacks the file:** Check Sent. If missing, send one short accurate follow-up rather than silently changing the story.
- **Someone already acted on the old version:** Ask where they got to and coordinate a correction as an ordinary collaboration task. “Ignore the previous copy” cannot undo completed work.
- **Recall says requested or failed:** Treat the old item as possibly visible and send a clear correction. Do not claim recall succeeded.
- **Content or recipients are uncertain:** Pause another file send and verify both. Route sensitive or managed information to appropriate support.

### Assumptions, alternatives, and side effects

Mail, chat, and cloud tools differ in undo, access, and upload behaviour. Check the current app and organisation rules rather than treating one product's button as universal. A screen reader or mobile device can use the attachment name, size, preview, and recipient list to check. A second message costs attention but makes the valid version clearer; it cannot guarantee deletion of the old copy.
